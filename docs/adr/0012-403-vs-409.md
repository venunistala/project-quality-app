# 12. Distinguishing 403 (forbidden) from 409 (conflict)

## Context

Every write service can reject a request for reasons that superficially look similar — "you can't
do that" — but map to two different HTTP semantics. `canTransition()` alone produces three distinct
denial reasons (`illegal-transition`, `requires-approver-role`, `creator-cannot-approve-own-release`),
and PATCH adds a fourth shape (editing a non-draft release). Picking the right status code for each
isn't cosmetic: a client's retry logic, caching, and error messaging all branch on 403 vs 409, and
picking wrong actively misleads whoever's consuming the API (including future us).

## Options considered

1. **Use 403 for every authorization-shaped rejection**, including illegal transitions. Simple
   single rule, but wrong for illegal transitions: an engineer trying to move a `deployed` release
   straight to `draft` isn't being denied because of *who they are* — an approver would be denied
   the exact same way, from the exact same state. Calling that 403 tells the client "you may never
   do this," when the true answer is "this specific move is invalid right now."
2. **Use 409 for every rejection that isn't a raw authentication failure**, including role and
   self-approval violations. Also wrong in the other direction: an engineer trying to approve a
   `submitted` release will never be allowed to, no matter what state the release is in — retrying
   after a refetch changes nothing. Telling the client "conflict, try again" when trying again can
   never succeed is actively misleading.
3. **Split by what would make the request succeed.** If a *different actor* making the identical
   request right now would succeed, the rejection is about permission — 403. If the *same actor*
   making the identical request from a *different release state* would succeed, the rejection is
   about the current state — 409.

## Decision

Go with option 3, applied consistently across every write endpoint:

- **403 — "you may never do this."** A fixed property of who's asking, independent of the
  release's current state: `requires-approver-role` (an engineer can never approve, from any
  state where approval is even legal), `creator-cannot-approve-own-release` (separation of
  duties — true regardless of state), and PATCH's `FORBIDDEN_NOT_CREATOR` (only the creator may
  edit, in any state where editing is otherwise legal).
- **409 — "this move is invalid from the current state."** Would be fine from a different state:
  `illegal-transition` (`canTransition`'s catch-all — this edge simply isn't in `TRANSITION_TABLE`
  from here), PATCH's `CONFLICT_NOT_DRAFT` (editing is fine in draft, forbidden everywhere else),
  and `CONFLICT_STALE_VERSION` (the release moved between load and write — refetching and retrying
  is exactly the right client action).

Order of checks matters and follows `canTransition()`'s own precedent: state-validity is checked
*before* permission (see `apps/api/src/services/releases-write.service.ts`'s `patchRelease` —
`CONFLICT_NOT_DRAFT` is checked before `FORBIDDEN_NOT_CREATOR`), because "is this move even
possible right now" is a more fundamental gate than "are you the one allowed to make it."

## Tradeoffs

- Gains: a client can mechanically decide what to do next from the status code alone — 403 means
  stop asking (nothing about retrying changes the outcome), 409 means refetch state and reconsider;
  the same discipline extends cleanly to every future write endpoint this app adds.
- Costs: requires a genuine judgment call per failure mode rather than one blanket rule, and that
  judgment call has to be re-made (correctly) every time a new authorization rule is added — the
  "would a different actor/state make it succeed" test above is the tool for making that call
  consistently.
